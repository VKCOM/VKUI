# Миграция с VKUI v7 на v8

## Определи объём миграции

Проверь `package.json` приложения, файл блокировки зависимостей, установленную версию VKUI и команды проверок. Уточни, на какую версию v8 нужно перейти. Если пользователь просит только оценить миграцию, перечисли необходимые изменения без правок в приложении. Если нужна сама миграция, обнови зависимость через менеджер пакетов проекта и внеси правки в пределах задачи.

Чтобы получить документацию API и примеры в текстовом виде, отправь заголовок `Accept: text/markdown` в запросе к `vkui.io` ([Accept Markdown](https://acceptmarkdown.com/)). Для перехода на версию 8.3.0 подойдёт такая команда.

```sh
curl -fsSL -H 'Accept: text/markdown' 'https://vkui.io/8.3.0/migrations/migration-v8/'
```

Если инструмент не позволяет задать заголовок или сервер возвращает HTML, поищи ссылку на `.mdx` на странице или в `llms.txt` целевой версии. В ссылках из индекса заменяй `https:/vkui.io/` в начале адреса на `https://vkui.io/`. Если ссылки нет или `.mdx` недоступен, прочитай HTML-страницу целевой версии. Это относится и к руководству по миграции, и к страницам компонентов и хуков.

Прочитай руководство целиком по адресу `https://vkui.io/{target-version}/migrations/migration-v8/`, прежде чем решать, какие изменения нужны. Если точная версия ещё не определена, обратись к `https://vkui.io/migrations/migration-v8/` и сообщи, что используешь актуальное руководство. Определи целевую версию v8 до изменения зависимостей. В репозитории VKUI исходник руководства находится в `website/content/migrations/migration-v8.mdx`.

Используй руководство как список проверок. Учти удалённые API, изменения в пропах и событиях, требования к браузерам и устаревшие API. В руководстве есть промпты для MCP. Применяй рекомендации из них напрямую, даже если упомянутые инструменты недоступны.

## Найди затронутый код

Найди импорты и реэкспорты из `@vkontakte/vkui`, в том числе импорты с псевдонимами и импорты вида `import * as`. При необходимости проследи, как используются локальные компоненты-обёртки и общие объекты пропов. Определяй применимость примера по тому, как используется API, даже если код отличается от примера до и после миграции.

Для каждого применимого пункта руководства отметь места в коде и запланированное изменение. Раздели обязательные правки для совместимости и необязательную замену устаревших API. Проверь отдельно, какие из устаревших API удалены в v8.

## Внеси изменения

Запусти подходящие преобразования из `@vkontakte/vkui-codemods` по инструкции в руководстве. Оставшиеся пункты миграции обработай вручную.

При сомнениях сверяй пропы и примеры с документацией целевой версии по адресу `https://vkui.io/{target-version}/components/{slug}/`. Ищи точные адреса страниц компонентов и хуков в `https://vkui.io/{target-version}/llms.txt` или в навигации по документации выбранной версии. Если опубликованная документация недоступна или в ней нет ответа, проверь установленные декларации или локальный исходный код целевой версии. Не подменяй их документацией другой мажорной версии.

Адаптируй примеры к логике приложения. Сохраняй колбэки, переходы состояния, псевдонимы импортов, рефы и существующие настройки.

- Переноси в задокументированный слот только пропы, которые предназначены для внутреннего элемента. Оставляй пропы корневого элемента на нём. Объединяй существующие `slotProps` и вложенные объекты слотов с новыми значениями.
- Проверь типы событий и `event.currentTarget`. При переносе обработчика на корневой или внутренний элемент могут измениться и тип события, и поведение обработчика.
- Сверяй имена слотов с API целевой версии. Имя HTML-тега и непроверенный пример могут дать неверное имя слота.
- При замене колбэков закрытия проверь, в какой момент они вызываются. Запрос на закрытие и завершение анимации происходят в разные моменты.
- Проверь требования к доступности. Если прежнее поведение нужно для совместимости, сохрани его. Добавляй или убирай `accessible={false}` с учётом того, как это повлияет на конкретный элемент.
- При переходе на `useModalManager` сохрани идентификаторы и параметры модальных окон, историю, восстановление фокуса и поведение при закрытии. Само появление нового API ещё не требует замены устаревшего.
- При замене `FixedLayout` на липкое позиционирование проверь контейнеры прокрутки и порядок элементов в документе, особенно для нижнего размещения. Проверь изменения вёрстки визуально.

## Проверь изменения и опиши результат

Запусти нужные проверки типов, линтер и существующие тесты. Просмотри изменения от кодмодов и ещё раз поищи использования старого API. Отметь допустимые использования, отложенные замены устаревших API и оставшиеся задачи миграции.

Проверь затронутые этапы жизненного цикла, события и рефы форм, элементы выбора даты, адаптивную вёрстку, клавиатурное управление и фокус. Укажи исходную и целевую версии, проведённые проверки и открытые вопросы совместимости.
